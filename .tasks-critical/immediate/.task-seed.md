  ## What the goal was

  Deliver one connected agency process:

  Signup → order/payment → materials → research/questions → accepted brief → specialist ToV + strategy →
  plan/topic → post review → consent/preparation, with employee intervention when needed.

  The key architectural decisions were:

  - Open Mercato owns authentication, persistence, workflows, queues and agent execution.
  - Teammate agency_tov is the sole ToV producer.
  - Our process orchestrates teammate services and preserves their exact saved outputs.
  - One journey supports fixture or live intelligence without replacing application behavior.
  - Produce a runnable server package and understandable demo instructions.

  The stored goal is paused, not completed. Its next revision needs to target main-indev and .demo-docs,
  replacing its outdated references to main and .dev-docs/demo.

  ## What is mocked—and what isn’t

  The application is not wholly mocked.

  - Fixture-backed: model intelligence and selected external source material.
  - Real application execution: authentication, scoped APIs, database records, attachments, native
    workflows, teammate producer code and explicit customer decisions.

  - Simulated payment: the approved zero-charge demo gateway, not real payment collection.
  - Entirely illustrative UI: the separate review/panel previews. Those are not evidence of completed
    customer work.

  - Disabled/unproved: publication and Discord sending; paid OpenRouter execution has not been demonstrated
    by us.

  - Missing functionality, not a mock: specialist correction continuation and app-connected source
    discovery.

  Also, the existing 1209dbd26 package predates the newer ToV integration. Successful packaging does not
  prove the current app.

  ## How I would parallelize next

  I’d prioritize these bounded tracks:

  1. Specialist correction delivery — direct agent.
     Wire saved client/QA feedback into the existing specialist revision producer, then fresh QA and
     review. No competing ToV generation.

  2. Current fixture demonstration — one direct runtime owner.
     Run the shared journey once, retain its native-run journal, and hand concrete failures to
     implementation owners. Preserve the database.

  3. Source discovery integration — separate implementation owner, if selected.
     Connect the teammate scout to an actionable intake path. Keep its files separate from correction work.

  4. Missing handoff observations — detached worker candidate.
     Add collection only where actual persisted lineage supports it. No invented success, new telemetry
     system or forced agent calls.

  5. Current server release — after a coherent source checkpoint.
     Build that revision once and test import/init/login/persistence. Don’t rebuild after every small
     change.

  Use direct agents first. A PowerShell sol high worker is useful for an exclusive, detached code island—
  not shared tests, builds, generators, servers or databases. Don’t launch extra workers merely to occupy
  capacity.

  ## The lean loop

  Choose outcome → reuse existing task/contracts → assign exclusive paths → implement → review one handoff
  → run affected checks → commit → next outcome.

  Keep one runtime owner and one Git owner. No repeated status polling, broad re-audits or documentation
  churn. Archive tasks and regenerate reports after actual delivery; reports should summarize work, not
  become the work.

  My recommendation: prioritize correction delivery and the current fixture run first, with detached
  evidence work alongside. Then package the resulting checkpoint. Decide whether automatic source discovery
  is required for the imminent presentation or whether staff-supplied corpus is acceptable for that
  milestone.
